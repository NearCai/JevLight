How it works

Signal control, mapped onto Jev

Jev is not a chat model: one request sends a state plus a map of typed questions, and returns one typed answer per question, evaluated in parallel. JevLight maps signal control directly onto that interface.

Traffic control
Intersection snapshot
Queue lengths, approaching vehicles by segment, waiting times — the target intersection and its direct neighbours.
"Which phase next?"
ETWT / NTST / ELWL / NLSL — which signal phase should serve next, per junction.
"Is this junction congested?"
A speculative question logged for analysis, riding along for free in the same request.
The decision
Chosen phase applied to SUMO via traci; every alternative stays visible for analysis.

Jev API
state (JSON)
Target intersection and direct upstream/downstream neighbours — current state only, one request per active junction.
choice question
One per intersection; the phases are the criteria. Jev evaluates all questions in parallel.
noul question
Speculative question in the same request — extra questions barely change latency.
answers.<id>
.choice / .probabilities / .confidence — a typed answer, full distribution, calibrated confidence.
Features

Built like infrastructure, not a demo

⚡

One call per active junction

Each active intersection receives one request with its own current state and its direct upstream/downstream neighbours. Requests do not expand to the whole road network.

🎯

Typed answers, not chat

Every answer ships with a probability distribution and a confidence score. Answers below --min_confidence are rejected and handled by fallback.

🛡️

Graceful fallbacks

Empty junctions never call the API (local waiting-time ranking). Failed, rate-limited or low-confidence requests keep the previous phase or fall back to the local ranking.

🧭

Two agent modes

jevlight — one agent per intersection with a purely local view; cojevlight (default) — one agent per intersection using its own state and direct upstream/downstream neighbours. Same Jev interface, two observation scopes.

🌐

Open local models

Jev is closed, but the open System One ecosystem converges on its wire format. Serve any checkpoint locally on vLLM — logit readout answers in a single prefill, no API key, no pacing.

🎥

Built-in 3D visualizer

Just add --visualize: a three.js viewer attaches to the run's own simulation with play / pause / step / speed controls — no build step, no separate SUMO.

Quick start

From zero to signal control

Prepare a model, start its service, and select an experiment configuration. This example uses Laya; each model has its own serving profile and environment.

1Clone & install

Install Python 3.11+ and uv, then create the project environment with SUMO.

git clone https://github.com/usail-hkust/JevLight.git
cd JevLight
uv sync --locked --extra sumo --extra preparation
2Prepare a model

Laya example: download weights and author sources, then install its model environment.

uv run --locked --extra preparation python \
  scripts/model_downloads/download.py --models laya
uv run --locked python scripts/model_downloads/fetch_sources.py
uv sync --locked \
  --project scripts/model_downloads/environments/encoder
3Start the model service

Set weights_path in serving.toml to your prepared model. Keep this terminal running.

uv run --locked \
  --project scripts/model_downloads/environments/encoder \
  python -m scripts.experiments.serve_decision_model \
  --config config/laya/serving.toml \
  --request-log results/laya/requests.jsonl \
  --batch-runtime native
4Run JevLight

In another terminal, inspect the selected JSON, then run it with whole-step batch requests.

uv run --locked python run_jevlight.py \
  --config config/laya/jevlight_jinan-1_s1.json \
  --jev_batch_size 196 --print_config
uv run --locked --extra sumo python run_jevlight.py \
  --config config/laya/jevlight_jinan-1_s1.json \
  --jev_batch_size 196
5Compare CoJevLight

Use the matching Co configuration to add direct-neighbour context under the same traffic condition.

uv run --locked --extra sumo python run_jevlight.py \
  --config config/laya/cojevlight_jinan-1_s1.json \
  --jev_batch_size 196
6Or use Jev API

Use the official API with an environment-variable key. Model preparation and a local service are unnecessary.

export TYPESAFE_API_KEY="your-api-key"
uv run --locked --extra sumo python run_jevlight.py \
  --jev_transport official --agent jevlight \
  --dataset jinan --count 3600

Choose traffic, mode and seed in config/<model>/*.json, and match jev_base_url to your running service. Batch requests use --jev_batch_size 196; the backend adjusts GPU chunk size to available memory. Add --visualize for the 3D viewer.

Using another model or existing downloads? See model preparation for the required environment, runtime, complete backbones and manifest layout, or the full setup guide.
